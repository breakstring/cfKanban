# cfKanban 1.12.0-rc.12

## 简体中文

相对 `1.12.0-rc.11`，本 RC 补齐 schema 30/31 首次部署，解决正式发行前默认新安装受阻的问题。

- 新实例可使用完整、已验证的 Service 工件生成首次部署计划，包含全部迁移的源与执行摘要。
- 部署在独立私有目录准备迁移执行副本，仅对已确认的 schema 30 SQL 应用固定兼容转换，保留已发布工件和数据库校验账本的原始摘要。
- 每次写入前重新检查工件、计划及执行副本；旧计划、被修改的副本或不明迁移结果会停止，不自动重试或接管同名资源。

## English

Compared with `1.12.0-rc.11`, this RC completes first deployment for schemas 30 and 31, fixing the default new-installation blocker before stable publication.

- New Instances can create a first-deployment plan from a complete verified Service artifact, recording source and execution digests for every migration.
- Deployment prepares migration copies in a separate private directory. Only the verified schema 30 SQL receives the fixed compatibility transform; published artifacts and database checksum records retain their original digests.
- Every write rechecks the artifact, plan and execution copies. Legacy plans, modified copies and unknown migration outcomes stop rather than retrying automatically or adopting same-name resources.

## 升级与已知限制 / Upgrade and known limitations

从 RC11 升级无新增数据库迁移，schema 保持 31，API 保持 0.1.0；仍须核对真实 ledger/schema。首次部署 schema 30/31 需要本版新计划，不能继续旧初装计划；尚未支持 schema 32 及更高版本。已确认迁移成功后，checksum 补记可在同一新建数据库、同一授权 journal 和完整 schema 读回下恢复；迁移执行结果不明时仍停止。隔离验收不代表已在 Cloudflare 创建并完成一个真实新实例。

Upgrading from RC11 adds no database migrations; schema remains 31 and API remains 0.1.0. Verify the actual ledger and schema. First deployment for schemas 30 and 31 requires a new plan from this release; legacy initial plans cannot resume, and schema 32 or later is not yet supported. After confirmed migration success, checksum recording can resume only for the same newly created database, authorized journal and complete schema readback. Unknown migration execution outcomes still stop. Isolated validation does not mean a real new Instance was created and fully deployed on Cloudflare.

实施与发行证据 / Implementation and release evidence: [CFK-733](https://cfkanban.dev/app/issues/CFK-733).
