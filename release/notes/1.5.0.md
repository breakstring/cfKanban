# cfKanban 1.5.0

## 简体中文

本正式版相对 `1.4.0` 统一登录后的工作台界面，新增个人主题，并改进语言切换、看板计数、局部更新和页面首次加载。业务实现沿用已验收的 `1.5.0-rc.2`，正式候选只收敛版本与发行说明。

- 所有已登录网页统一采用 Nuxt UI 组件，覆盖看板、Issue 详情、新建、工作列表、项目选择、个人设置及管理页面，调整表单、按钮、弹窗和菜单，并补齐桌面/移动布局、焦点管理和键盘操作。
- 个人设置提供默认的「暖橙」与「静蓝」主题，按 Principal 保存在服务端，重新登录或更换浏览器后仍可使用。Web 与 Agent 使用同一资料 API 读取和保存主题；主题只改变配色，保存失败保留草稿，迟到响应不会覆盖已确认的新偏好。`PATCH /api/v1/me` 可携带 `expected_version` 修改姓名、主题或两者，并可使用 `Idempotency-Key` 重试原请求；现有仅改姓名的请求保持兼容。
- 账户菜单集中展示姓名、身份和账户操作，会话到期时间及适用时的首选域名链接移至页脚。看板统一提供「项目设置」，按当前权限进入管理、标签、活动和已删除页面，返回同一项目时保留已提交筛选。
- 全局语言入口使用通用翻译图标，提示和无障碍名称说明当前语言与切换目标，业务弹窗不再重复提供入口。切换语言保留未保存草稿；默认状态名称仍为英文，自定义状态名称和业务内容保留原文。
- 看板五列展示当前已提交筛选条件下、各状态未删除 Issue 的真实匹配总数。独立的项目 Issue 计数 API 也可由 Agent 使用，无需遍历所有分页。计数与卡片列表分别处理加载、失败和显式重试，计数失败不会显示为零或阻塞已有卡片；列表和计数是独立读取，并发外部写入后可显式刷新核对。
- 新建、状态移动、完成和优先级修改按服务端确认的 Issue 局部更新卡片，保留已加载页、可用 cursor、其他卡片和列滚动位置，丢弃受影响的迟到分页响应。CAS 冲突和不确定结果先读回事实，不自动覆盖草稿或重放业务写入；实时权限、幂等和原子审计继续由服务端执行。
- 公开首页恢复覆盖整个视口的连续暖色背景，修正页头/页脚的宽度、对齐、换行及窄屏触控布局，认证页主题不再覆盖首页画布。
- 全部 11 个业务 View 按需加载，Nuxt UI provider 与认证页头只在认证路径加载。加载失败提供显式重试和用户触发的刷新，离页后忽略旧加载结果，刷新沿用草稿保护。构建和 Service 打包核对 HTML、manifest、静态/动态引用及资源闭包，并强制入口 gzip ≤90,000 B、入口同步 JS 闭包 ≤95,000 B、最大 JS chunk ≤90,000 B 的预算。
- 加固会话重新验证和项目切换的竞态处理，避免旧请求覆盖新会话。会话仍从创建起固定有效 8 小时，刷新、切换项目及操作不会延长到期时间；自动续期不包含在本版中。
- 普通安装继续默认发现 stable，并先识别 Agent 宿主能力。支持 Git 来源的宿主可跟随只承载正式发行的 main；目录型宿主使用完整已验证 bundle。默认发现不固定安装 ref，显式历史版或 RC 仍固定准确发行；每次操作继续固定 immutable manifest、版本及工件摘要，并核对实际安装内容与加载状态。

首次加载测量来自 RC 开发阶段的本地生产产物与合成 API，不是线上性能结果。七个场景各三次、同条件冷缓存与网络/CPU 节流下，公开首页全部首屏 JS gzip 从 258,757 B 降至 92,563 B，可交互中位数从 2,463.9 ms 降至 1,513.0 ms。三次采样早于最终翻译图标微调；最终图标后的单次快速复核不代替这些中位数。按需加载使首次首页→看板和详情→管理分别增加约 988 ms、1,071 ms，全部 chunk gzip 合计也略增，不能将首屏改善外推为全部体积、CPU 或线上成本下降。方法、数据与限制见[性能基线](https://github.com/breakstring/cfKanban/blob/1.5.0/docs/research/2026-10-01-web-initial-load-performance.md)。

## English

Compared with `1.4.0`, this stable release unifies the signed-in workbench, adds personal themes, and improves language switching, board counts, local updates, and initial page loading. Business behavior follows the accepted `1.5.0-rc.2`; the stable candidate only updates version metadata and release notes.

- All signed-in pages use Nuxt UI components across boards, Issue details and creation, work lists, project selection, personal settings, and management. Forms, buttons, dialogs, and menus have consistent desktop/mobile layouts, focus management, and keyboard interaction.
- Personal settings offer default Warm orange and Calm blue themes, stored on the server for each Principal and available after signing in again or changing browsers. Web and Agent clients use the same profile API to read and save themes. Themes only change colors; failed saves retain drafts, and late responses cannot overwrite a confirmed newer preference. `PATCH /api/v1/me` accepts `expected_version` with a name, theme, or both, and supports `Idempotency-Key` for retries of the original request. Existing name-only requests remain compatible.
- The account menu groups the user's name, role, and account actions. Session expiry and the preferred-origin link, when applicable, move to the footer. A single Project settings entry exposes Management, Labels, Activity, and Deleted pages according to current permissions and preserves committed filters when returning to the same project.
- A universal translation icon provides the global language control, with a tooltip and accessible name describing the current language and switch target. Business dialogs no longer duplicate it. Language changes preserve unsaved drafts; default status names stay in English, while custom status names and business content retain their original text.
- All five board columns show actual matching totals of non-deleted Issues for committed filters. Agents can use the independent project Issue count API without traversing all pages. Counts and card lists have separate loading, failure, and explicit retry states; failed counts neither appear as zero nor block existing cards. Lists and counts are separate reads, so an explicit refresh can reconcile concurrent external changes.
- Creation, status moves, completion, and priority changes update cards locally from server-confirmed Issues, preserving loaded pages, usable cursors, other cards, and column scroll positions. Stale pagination responses for affected columns are discarded. CAS conflicts and uncertain outcomes first read back facts, without automatically overwriting drafts or replaying writes. The server continues to enforce current authorization, idempotency, and atomic audit records.
- The public homepage restores a continuous warm background across the viewport and fixes header/footer width, alignment, wrapping, and narrow-screen touch layouts. Signed-in themes no longer override the homepage canvas.
- All 11 business Views load on demand, while the Nuxt UI provider and signed-in header load only on authenticated routes. Failed loads offer explicit retry and user-triggered refresh; departed pages ignore older load results, and refresh retains draft protection. Builds and Service packaging validate HTML, the manifest, static/dynamic references, and the asset closure, enforcing gzip budgets of entry ≤90,000 B, entry synchronous JS closure ≤95,000 B, and largest JS chunk ≤90,000 B.
- Session revalidation and project switching handle races so older requests cannot overwrite a newer session. Sessions still expire eight hours after creation; page refreshes, project switches, and activity do not extend expiry. Automatic renewal is outside this release.
- Ordinary installation continues to discover stable and first identifies the Agent host's capabilities. Git-backed hosts can follow main, which contains published stable releases; directory-based hosts use the complete verified bundle. Default discovery leaves the installation ref unpinned, while explicit historical or RC selections retain an exact release. Each operation still pins the immutable manifest, version, and artifact digests and verifies installed content and loading.

Initial loading measurements use local production artifacts and synthetic APIs from RC development, rather than online performance. Across seven scenarios sampled three times with consistent cold caches and network/CPU throttling, the public homepage's total initial JS gzip fell from 258,757 B to 92,563 B, and its median interaction endpoint fell from 2,463.9 ms to 1,513.0 ms. These samples precede the final translation icon adjustment; subsequent single quick checks do not replace the medians. On-demand loading adds about 988 ms to the first homepage→board navigation and 1,071 ms to the first details→management navigation, and summed gzip across all chunks increases slightly. Smaller initial loads do not establish lower total size, CPU cost, or online costs. See the [performance baseline](https://github.com/breakstring/cfKanban/blob/1.5.0/docs/research/2026-10-01-web-initial-load-performance.md) for methods, data, and limitations.

## 升级说明 / Upgrade notes

从 `1.4.0` 升级时，唯一新增的 D1 migration 为 `0014_principal_theme.sql`，须先应用它将 schema 从 `13` 升至 `14`，再部署新版 Worker。迁移为 Principal 增加默认 `orange`、允许 `orange / blue` 的主题字段，不删除既有数据。已使用 `1.5.0-rc.1` / `1.5.0-rc.2` 且 ledger 与实际 schema 均确认是 `14` 的实例无需新增迁移。Owner 恢复工具支持 schema 14；Worker 回滚不会回退 D1。

When upgrading from `1.4.0`, the only new D1 migration is `0014_principal_theme.sql`. Apply it to advance schema `13` to `14` before deploying the new Worker. It adds a Principal theme field defaulting to `orange` and allowing `orange / blue`, without deleting existing data. Instances on `1.5.0-rc.1` / `1.5.0-rc.2` with both the ledger and actual schema verified as `14` require no new migration. Owner recovery tooling supports schema 14; a Worker rollback does not roll back D1.

API 兼容版本保持 `0.1.0`，发行 manifest 保持 schema `2`；使用兼容此格式和本发行的 Skills，并按固定清单执行升级。没有新增云资源、付费要求或权限。本机 Skills 更新、宿主实际加载与实例升级分别核对；文件更新不代表当前对话已经加载新技能。

The API compatibility version remains `0.1.0`, and release manifests remain schema `2`. Use Skills compatible with this format and release, and upgrade from the pinned manifest. No cloud resources, paid requirements, or permissions are added. Local Skill updates, actual host loading, and instance upgrades require separate verification; updated files do not establish that an existing conversation has loaded new Skills.
