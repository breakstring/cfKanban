# cfKanban 1.12.0-rc.11

## 简体中文

相对 `1.12.0-rc.10`，本 RC 简化工作区与项目趋势体验，并补充工作区描述。

- 工作区趋势并入工作区设置，仅实例 Owner 和本工作区管理员可见，汇总全部未归档项目。
- 工作区支持可选描述，可在设置中修改或清空，Web、CLI 与 Skills 保持一致。
- 移除趋势页的项目清单、历史覆盖明细和每日数值展开，保留悬浮及键盘查看每日数值。
- 里程碑图使用“完成进度”名称，项目的里程碑与趋势切换补齐一致图标。

## English

Compared with `1.12.0-rc.10`, this RC simplifies Workspace and Project trends and adds Workspace descriptions.

- Workspace trends now lives in Workspace settings, is available only to the Instance Owner and that Workspace's administrators, and includes every unarchived Project.
- Workspaces support an optional description that can be edited or cleared through consistent Web, CLI and Skill workflows.
- Remove Project lists, detailed historical coverage and expandable daily tables; retain per-day values through hover and keyboard focus.
- Rename milestone charts to “Milestone progress” and give milestone and trend view switches matching icons.

## 升级与已知限制 / Upgrade and known limitations

从 RC10 升级需执行唯一新增迁移 `0031_workspace_description.sql`，schema 30 → 31，API 版本仍为 0.1.0。旧工作区描述默认为空；已有事项和趋势历史不需要重新回填。工作区趋势不再支持 REST `?project=`、CLI `--project` 或 MCP `project_ids`；普通成员、项目管理员及固定项目/事项会话不能读取工作区聚合，项目和里程碑趋势权限不变。工作区超过 100 个未归档项目时显式拒绝，不返回部分统计。

Upgrading from RC10 requires only the new `0031_workspace_description.sql` migration, moving schema 30 to 31 while API version remains 0.1.0. Existing descriptions default to null; Issue and trend history needs no new backfill. Workspace trends no longer accepts REST `?project=`, CLI `--project` or MCP `project_ids`. Ordinary members, Project administrators and fixed Project/Issue sessions cannot read the Workspace aggregate; Project and milestone trend permissions remain unchanged. Workspaces with more than 100 unarchived Projects are rejected explicitly rather than returning partial statistics.

schema 31 首次安装仍暂不支持，新安装使用 stable。升级后若需回填，须使用 schema 31 的新升级回执与匹配的不可变 Service 工件重新计划，不复用旧 schema 30 回填操作。

First installation of schema 31 remains temporarily unsupported; use stable for new installations. Any backfill after upgrading requires a new plan bound to the schema 31 upgrade receipt and matching immutable Service artifact, rather than reusing a schema 30 operation.
