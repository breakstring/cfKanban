# Optional public access and cost protection

The default remains Workers Free with bundled Static Assets and the existing application limits. No command in this workflow buys a domain, purchases or upgrades a Cloudflare plan, installs Turnstile, or enables a WAF profile implicitly. A paid Worker CPU ceiling applies only when the operator explicitly confirms an existing paid Workers plan; it is a per-invocation ceiling, not an account billing cap. Native rate limits are approximate, per-location controls rather than globally exact budgets.

## Worker CPU ceiling

Use `cfkanban deploy worker cost-settings --input-file worker-readback.json` (Skill helper `runtime worker-cost-settings`) with the exact `accountId`, `workerName`, absolute `wranglerExecutable` and the existing `cloudflareProfile` or private `contextDirectory`. This reads the selected production environment's `script.limits` and does not inspect or change a subscription.

Before every existing Instance upgrade, including one after attaching from a second computer, copy the returned `worker_limits` exactly into `resources.worker.worker_limits`; explicitly use `null` only when the readback returns it. This snapshot contains only provider configuration (`cpu_ms` and/or `subrequests`), never a plan subscription claim. Missing snapshots stop planning with a command to perform the readback. Omit `workerLimits` to preserve every observed limit, including Free defaults such as `{ "cpu_ms": 10, "subrequests": 50 }`, without declaring a Paid plan.

To set or replace the CPU ceiling explicitly, add `workerLimits: { "workers_plan": "paid", "cpu_ms": 100 }` to `deploy upgrade plan`. This is the Owner's confirmation of an existing Paid subscription, not evidence inferred from Worker metadata; the command does not inspect or purchase a subscription. CPU values are integers from 1 to 300000. The plan records this request separately as `cpu_limit_request`, changes only `cpu_ms`, and preserves the exact observed `subrequests`. Explicit removal, Free-plan change requests, and unknown limit fields are rejected. The generated Wrangler config preserves the whole frozen target limits object; apply and finalization compare the whole object before/after deployment. Drift stops the operation for a new readback and plan. First deployment has no existing limits to preserve and does not generate a limits block.

A source release with the anonymous-login and expensive-read protections generates their native bindings alongside existing rate limits. Normal upgrades preserve a verified current policy. Login denial occurs before challenge creation or verification; persistent challenge cleanup claims limit routine cleanup work across isolates. These controls reduce work but are not exact global cost caps.

## Custom domain plan and apply

Select one unused lowercase hostname in an active Cloudflare zone belonging to the receipt's account. Use the existing private deployment receipt, the current authenticated Deployment Owner, and an already authorized Cloudflare profile/context. Cloudflare access must cover Worker routing and read the selected zone/DNS. WAF privileges are unnecessary for domain-only setup. The helper never broadens OAuth scopes or substitutes another account.

1. `cfkanban deploy public-access inspect --input-file public-access-inspect.json` maps to `public-access inspect`. Inputs: `instanceId`, `receiptPath`, `zoneId`, `hostname`, absolute `wranglerExecutable`, and exactly one `cloudflareProfile` / `contextDirectory`. Use `includeWaf: false` for domain-only inspection. No resource write occurs.
2. `cfkanban deploy public-access plan --input-file public-access-plan.json` maps to `plan public-access`, adding `taskId`, optional `operationId`, and `mode: "domain-enable"`. For either domain enable or rollback, explicitly set `passkeyRecoveryReady: true` only after same-identity recovery and new-hostname registration are prepared; omission remains false and apply refuses the cutover. The plan freezes this declaration and the old/new RP IDs in `passkey_impact`. It verifies the current Owner, exact Worker/D1 receipt, active zone, complete routing inventory, empty selected DNS name, and an enabled workers.dev origin. Existing custom-domain mappings, DNS records, Worker routes, wildcard domains and partial inventories are rejected rather than adopted or overwritten.
3. Present the complete plan, new URL, old-origin closure and affected clients. The plan performs custom-domain attachment, same-Instance credential-free HTTPS discovery, an Owner CAS preferred-origin update, both-origin discovery, local trusted-origin rebind, authenticated new-origin readback, then disables both workers.dev and preview URLs. Existing Passkeys belong to the old RP hostname and do not transfer. Web-only users need an existing same-identity API connection or Owner-issued same-Principal recovery, then registration of a new Passkey. The new-origin Owner API readback proves the Owner recovery path; it does not prove every user has migrated. API clients must update trusted origin and old links stop working when the old origin closes. These are explicit cutover effects. DNS/TLS propagation failure stops with the old origin available until the new origin has been proved.
4. Public `deploy public-access apply` / `resume` take the same `plan`, `instanceId`, `operationId`, `taskId`, and `authorization: { "instance_id": "…", "operation_id": "…", "task_id": "…", "plan_digest": "…" }`. The public CLI creates/authorizes the matching journal. Skills use `journal create`, `journal authorize`, then `public-access apply`. Existing user authorization for this exact plan remains valid; do not ask for each step.

A response failure may follow a committed control-plane write. Retain the exact plan, journal, original idempotency key and ownership reference; `resume` reads the actual mapping/rule/origin before continuing and reauthenticates Owner before further writes. Never generate a replacement operation to bypass an uncertain outcome. Per-call private process locks stop concurrent operations. Resume reclaims only uniquely named lock files whose recorded process ID is proven stopped, including an empty or partial file left by a crash; a live or unverified process remains a blocker. No token or one-time credential is returned.

## Optional Free WAF profile

After domain enable completes, use a separate `mode: "waf-enable"` plan. The current profile, `anonymous-api-filter`, consumes one custom-rule slot and acts only on the exact hostname plus known private API paths missing both an Authorization header and the session-cookie name. Public login, discovery and join flows remain available. Forged header/cookie presence can bypass this negative filter; the Worker must still authenticate every private request. The profile reduces anonymous invalid traffic and does not promise DDoS prevention or a request/billing cap.

Cloudflare Free custom rules have a five-rule allowance. The helper inventories the phase and refuses if a verified free slot is unavailable, regardless of any paid capability. Free rate-limiting expressions do not support Host, so this workflow does not install a zone-wide rate-limit rule that might affect another site. It never uses a challenge action or Turnstile. The selected existing Cloudflare authentication needs the corresponding custom-rules read/write permission; a failure stops without an implicit login or scope expansion.

Only a tool-owned rule is created/deleted through individual Rulesets API endpoints. Its exact reference, rule ID, ruleset ID, content and private ownership receipt must agree. Unrelated rule content is checked before and after writes; the tool never replaces an entire shared-zone ruleset. Competing edits detected during readback stop completion; Cloudflare control APIs do not provide application CAS for these changes.

`mode: "waf-disable"` removes only that exact owned rule and leaves the custom domain in place. It never deletes the shared ruleset or another rule. `mode: "domain-rollback"` first enables the proven original workers.dev origin with previews disabled, verifies and migrates origin trust back, removes the owned WAF rule when present, and detaches only the owned custom-domain mapping. It does not delete certificates or unrelated DNS records.

## Upgrades and status

The verified non-secret ownership snapshot is stored in this Instance's private `receipts/public-access.json`. For a normal upgrade, carry this complete receipt in `resources.public_access`, set `resources.workers_dev: false`, `resources.custom_domain` to its exact hostname, and keep routes empty. The normal upgrade preserves that existing custom domain, disabled workers.dev/preview URLs and exact owned WAF profile; it cannot enable, repair, adopt or remove them. Apply verifies the private receipt and live Cloudflare routing/rule before and after deployment. Missing receipt, changed exposure or changed rule stops the upgrade. After an authorized domain rollback, carry its inactive ownership receipt in `resources.public_access`, keep `resources.workers_dev: true` and `resources.custom_domain: null`; the upgrade verifies that the managed mapping is absent, preserves disabled previews, and removes old snapshot bindings.

The next normal upgrade projects `PUBLIC_ACCESS_MODE`, `PUBLIC_ACCESS_HOSTNAME`, `PUBLIC_ACCESS_WAF_PROFILE`, `PUBLIC_ACCESS_RULE_REF` and `PUBLIC_ACCESS_VERIFIED_AT` as non-secret Worker variables for Owner status. They are the last deployment's verified snapshot, not real-time WAF telemetry. Domain/WAF apply writes its verified local receipt and does not silently redeploy an unknown Worker just to refresh that display. Run `public-access inspect` for current control-plane evidence.

For another computer, pass the explicitly supplied non-secret `publicAccessReceipt` to `deploy attach inspect` / `deploy attach plan`. Attachment verifies the same Instance and Owner plus exact live domain, zone, workers.dev/preview status and owned rule, then saves the receipt locally without cloud writes. It rejects a disabled workers.dev setup without that receipt and never reconstructs ownership from a hostname or status variables. Transfer no API or Cloudflare secret as ordinary input.
