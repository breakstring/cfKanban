# CFK-497：Issue 筛选查询的本地成本证据

日期：2026-09-29。此文是可复现实验快照，不代表线上 D1 读取量或延迟承诺。

## 环境与计量边界

- Wrangler 4.127.1 的 `createTestHarness` 内部固定 `127.0.0.1:0`、`persist:false`；`wrangler.wp02-test.jsonc` 使用全零 D1 UUID，无远端绑定。实验仅在临时本地 D1 中建数据与索引。
- 调用真实 `listIssues` / `listIssueCandidates`，记录服务端最终带权限 guard 的 Issue 查询及其绑定参数，对该 SQL 执行 `EXPLAIN QUERY PLAN`，从 D1 返回的 `meta.rows_read` 读出行读取量。
- 表中的“返回”是 API 返回的 Issue 数；SQL 为判断下一页会取 `limit + 1`。读取量包含最终 SQL 的权限、关联查询与结果装配，**不包含**其他独立权限重验、标签装配等 SQL，因此不是整次 HTTP 请求的总消耗。
- 延迟是本机 Node 到本地 D1 的单条结果 SQL 调用耗时，包含本地调用开销。测试同时输出 service 调用总时长；不将本地毫秒数推断成生产延迟。
- 数据包含 36 条语义用例及另两个项目的 2,400 / 12,000 条成本用例。成本用例两个项目各占一半；稀疏状态、负责人、优先级和标签每 100 条出现一次，密集标签每 4 条出现一次（排除稀疏标签项）。不同更新时间使用重复时间戳，分页必须以 Issue number 破同值。

D1 的 `rows_read` 是查询访问的行数，而非返回行数；索引优化读取也会增加维护索引的写入成本。依据：[Cloudflare D1 索引说明](https://developers.cloudflare.com/d1/best-practices/use-indexes/)与 [D1 返回对象](https://developers.cloudflare.com/d1/worker-api/return-object/)。

## 对照方法

旧形状对照在同一数据库、同一数据上运行，保留真实服务查询的当前授权 CTE 与完整结果投影，将 `issue_page` 换回“先按项目索引扫描，再按筛选条件检查、排序、LIMIT”的旧形状，并固定原 `idx_issues_project_list`。断言对照与当前查询返回完全相同的编号和顺序。

这是明确限定的**查询形状对照**，并非重新运行完整旧发行包。优先级是新能力，对照中仅将优先级条件放在旧形状的残余筛选位置；旧 API 本身没有此参数。标签也为新能力，不给出虚构的旧 API 标签筛选数据。

复现入口：

```sh
node --experimental-strip-types --test scripts/tests/issue-query-filters.integration.test.mjs
node --experimental-strip-types --test scripts/tests/issue-query-indexes-migration.test.mjs
```

实际计划中，状态、负责人、优先级分别命中 `idx_issues_active_status_order`、`idx_issues_active_assignee_order`、`idx_issues_active_priority_order`，按项目及驱动值等值定位；每个分支先取 `limit + 1`，再归并到全局一页。结果装配、授权视图与最终分支归并仍可能使用临时排序；不能把“无 Issue 全表扫描”表述为“整条 SQL 没有排序”。

稀疏匹配收益明显；原本很密集的筛选已经能很快找齐一页，新分支归并会增加小幅或固定读取开销。两项目、两个状态的 209 行在五倍数据增长后保持相同，未承诺每一种数据分布都比旧形状更少。

标签计划从请求 UUID 驱动，先验证标签仍有效且属于当前可见项目，再通过 `idx_issue_labels_label_issue(label_id, issue_id)` 读取匹配 Issue ID。用 `CROSS JOIN` 固定该顺序，避免优化器先遍历项目内所有标签和关联。标签匹配集合去重后按 Issue 排序；读量随**匹配关联数**增长，密集标签及其后续页并不是常量成本。

组合条件使用一个索引作为驱动，其余条件继续在服务端分页之前筛选。状态、负责人、优先级的任意交集、标题子串、阻塞关系以及 `needs_reassignment` 都不保证 `O(limit)`；测试仅对具体有界场景设阈值，不以单列索引存在推断任意组合的低成本。

`unassigned` 常是大集合，因此包含它的组合优先由 priority/status 索引驱动，而具体负责人仍优先使用 assignee 索引。上述两个交集刻意让稀疏条件与未分配集合完全不相交，避免只验证恰好相关的样本；读取 137 行来自检查较小的候选集合。这是可解释的启发式选择，不依赖运行时统计，也不是任意分布的全局最优计划。

## 候选查询

12,000 条成本用例上，候选保持 `todo` 和显式 assignment 策略；结果 SQL 命中 `idx_issues_todo_assignee_order`。

| 查询 | 页 | rows_read | 返回 | SQL 耗时 ms |
| --- | ---: | ---: | ---: | ---: |
| mine + none | 1 | 139 | 10 | 4.87 |
| mine + none | 2 | 149 | 10 | 8.67 |
| unassigned + high | 1 | 128 | 10 | 8.82 |
| unassigned + high | 2 | 138 | 10 | 5.16 |
| mine + urgent，无匹配 | 1 | 32 | 0 | 3.94 |

额外语义回归覆盖多项目、多优先级分支的全分页，分别核对 `mine / unassigned / needs_reassignment` 的排序、无重复和完整性；标签分支另外验收同维度 OR、不同维度 AND、未知/已删除/越界标签、固定 Session scope、参数数量上限、非法 UUID、游标绑定及软删除列表。

## 写成本与迁移

新增四个兼容索引，均不重建表、不改写旧 migration。三个普通列表索引只收录未删除 Issue，候选索引只收录未删除且为 `todo` 的 Issue。

在同一临时本地数据库中对照有无这四个索引的 D1 `meta.rows_written`：

| 操作 | 原索引 | 新增四索引后 |
| --- | ---: | ---: |
| 插入一个 todo Issue | 8 | 12 |
| 同时改变负责人、优先级和 updated_at | 5 | 9 |
| 将 Issue 软删除 | 4 | 4 |

本地计数没有将此软删除产生的索引条目移除体现为额外 `rows_written`；不据此推导线上删除计费或“索引移除没有代价”。

存储测量独立使用 Node 内置 SQLite `dbstat` 和 `PRAGMA page_count/page_size`，页大小为 4,096 字节。复用同样 12,000 条成本数据的状态、优先级、分配、时间戳分布、36 字节 UUID 和 3,000 个标签关联，并保留迁移回归基础夹具中的 40 条 Issue（4 条有效、36 条已删除）；不将本地页大小统计当作线上 D1 账单。

| 新索引 | dbstat 页字节 | 索引条目 |
| --- | ---: | ---: |
| 普通状态排序 | 675,840 | 12,004 |
| 普通负责人排序 | 634,880 | 12,004 |
| 普通优先级排序 | 675,840 | 12,004 |
| todo 候选负责人排序 | 643,072 | 11,880 |
| 合计 | 2,629,632 | — |

数据库页占用从 6,537,216 字节（约 6.23 MiB）增至 9,166,848 字节（约 8.74 MiB），增加约 2.51 MiB、40.23%。本样本 Issue body 为空，既有数据体积较小，所以相对增幅明显；实际长正文、评论、事件等会改变这个比例。四个索引的绝对存储增长、Issue 写入增加，与稀疏筛选和无匹配查询减少行读同时存在。是否划算取决于查询频率、写入频率、匹配分布和正文规模；不据此预测账户费用或额度。实验未测量线上数据库大小、远端延迟或真实账户配额。

迁移回归验证 schema 12 → 13 后既有数据、事件序号、旧索引、约束、授权视图保持一致；失败时四个新索引和版本号一起回滚；重复应用拒绝，ledger 存在但新索引缺失时读回停止；校验此前 migration 的 checksum 未改变。

本次定向运行：查询/行为集成 9/9、迁移回归 5/5 通过。性能门槛及可复现数据集保存在上述测试中。
