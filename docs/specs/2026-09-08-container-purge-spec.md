# 工作区与项目归档及永久删除合同

- 状态：Frozen
- 冻结依据：2026-09-08 用户明确同意两步实施，并授权已归档项目、空工作区永久删除
- 合同修订：2（容器身份按 UUID SPEC 更新）
- 本修订替代 Foundation / API / Web / Agent Skills 合同中“v0 不提供业务物理删除”的限制，仅限本文件明确的容器清理能力。其他资源仍不提供单独 hard-delete。

## 1. 用户行为

归档沿用既有 soft-delete / restore，停止访问并保留内容与权限；恢复仍提示可能重新开启的公开加入。Web 统一使用“归档 / 恢复”，不改变 wire 中的 `deleted_at`、DELETE 或 restore。

仅 Deployment Owner 可永久删除已归档项目，或已归档且没有未永久删除项目的工作区。非空工作区必须先逐个清理项目，无公开批量删除。删除不可恢复，不自动定期清理。

Web 只在归档列表提供永久删除入口；同名对象显示消歧提示并可展开完整 UUID、所属工作区及可用业务详情。删除弹窗保留该目标的识别信息，先加载准确目标及影响预览，用户输入完整显示名称后才可确认。API 和 Skill 同样要求目标版本、确认名称和预览摘要，不能绕过当前权限、CAS、幂等与最终事务校验。

## 2. 清理与保留

项目永久删除清除该项目事项、普通与完成评论、标签及绑定、涉及本项目任一端的关系、项目授权、状态显示名称、公开加入策略和用量记录，以及绑定本项目的 Browser Launch / Project 或 Issue Session。

包含该项目的未兑换邀请先撤销，再移除本项目的邀请及兑换关联；多项目邀请的其他项目既有 Grant 不受影响。影响预览必须说明受影响邀请数量及其中共享邀请数量。保留与其他项目有关的邀请记录，不允许把仍有效邀请静默缩小为剩余项目。

清除本项目及两端关系的历史事件和对应幂等响应 / 操作快照，避免正文和评论仍占用响应缓存。保留一次精简的 Owner 删除审计与本次删除的幂等结果；对仍存在的关系另一端项目记录不含被删除项目敏感内容的关系清理提示。删除旧事件可能使旧分页游标失效，调用者必须重新读取。

容器仅保留不可恢复的最小记录：稳定 UUID、归属与删除审计所需字段。清除原显示名称、项目说明和配额等业务字段；最小记录从正常及归档列表排除。名称可重复，UUID 不复用，Issue AUTOINCREMENT 序列不重置。工作区中仅余此类最小记录视为业务上为空。

该功能清理数据库业务行，不运行 VACUUM、D1 Time Travel 或平台恢复，不承诺 Cloudflare 账面存储即时同比例下降，也不清理外部系统、平台备份或客户端已保存副本。

## 3. API 与并发

- `GET /api/v1/workspaces/{workspace_id}/purge-preview`
- `GET /api/v1/workspaces/{workspace_id}/projects/{project_id}/purge-preview`
- 对应目标 `POST .../commands/purge`
- POST body：`expected_version`、`confirm_name`、`preview_digest`；必须携带独立 `Idempotency-Key`。
- 预览包括稳定 ID、显示名称、版本、资源计数、跨项目关系与共享邀请影响、是否可删除及停止原因；摘要绑定目标与影响。
- 执行时再次核对 Owner 当前身份、归档状态、版本、确认名称与预览。最终 D1 原子批次重新校验影响计数，预览漂移不执行删除。
- 所有清理语句共享目标操作标记门控；删除、精简审计、不可恢复标记与幂等快照在同一事务中完成。中途失败必须全部回滚；提交响应丢失以相同请求恢复，不能重新执行不同删除。
- purged 标记与归档状态保持数据库不变量；restore 和所有容器列表 / 读取必须排除 purged，旧路径不能复活最小记录。

## 4. 验证要求

验证参与者拒绝、活跃目标拒绝、非空工作区拒绝、名称 / 版本 / 预览漂移、restore 竞争、事务回滚、幂等重放、跨项目关系、共享邀请、Session 失效、历史正文清除、UUID / Issue 编号不复用及列表排除。所有测试使用本地隔离数据库，不操作线上资源。

界面保留紧凑父子分组和工作区内创建项目入口；移除关系教程、重复层级标签及含糊的项目搜索框。2026-09-08 用户确认进一步调整：在“操作记录”之后增加独立“已归档内容”分区，常规列表只显示使用中的内容；归档列表按工作区组织已归档项目，分成“已归档项目”（按未归档父工作区分组）和“已归档工作区”两个区域，避免混用状态徽标和操作；空的已归档工作区仍可见。恢复与永久删除采用同类按钮，仅区分危险色。两个分区的工作区均默认折叠，点击展开子项目；永久删除经服务端确认后原地移除对应项，不重建列表或丢失其他分组的展开状态。永久删除确认框在输入框上方按目标类型展示完整名称，名称以可点击复制的色块呈现并在预留的固定位置提供成功/失败反馈，不改变弹窗高度；点击只复制名称，不自动填写或提交确认。

## 5. 迁移与交付边界

当前容器身份与 schema 3 的后续迁移以 [UUID 重构合同](2026-09-08-container-uuid-spec.md) 为准。以下保留初次引入归档永久删除能力的 schema 2 迁移说明。

`0002_container_purge.sql` 在既有 schema 上添加 Workspace/Project 的 `purged_at` 和查询索引，将 schema version 更新为 2；不改写已发行的初始 migration，也不在迁移时清理业务数据。首次 bootstrap 使用 manifest 的 schema version。新 Worker 上线前必须先通过既有部署流程应用并读回此迁移；本次本地实现不代表线上已迁移或已开放删除能力。存在永久删除记录后，旧 Worker 不理解这些记录，不应回滚到不支持该增补的版本；数据库约束仍阻止其恢复永久删除记录。
